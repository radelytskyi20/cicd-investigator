# T01-03: Orchestrate the local stack with Aspire

**Stage:** 1
**Depends on:** [T01-02](T01-02.md)
**Status:** Done

## Stack

Aspire AppHost; Aspire SQL Server hosting and JavaScript integrations; Docker; MS SQL Server; EF Core SQL Server provider; ASP.NET Core health checks.

## Goal

Start the database, API, MCP server and frontend from one AppHost command and commit the working foundation.

## Implementation
1. Declare a SQL Server container and named database in AppHost. Publish configurable host port 14330, reject host port 1433, check port availability, and retain container port 1433. Pass connection configuration through Aspire and keep credentials in local secrets. Do not add a competing docker-compose orchestrator.
2. Register API, MCP host and Vite resources. Provide the frontend with the actual API address and the API with the MCP endpoint. Aspire owns one MCP process; the agent will connect to it over HTTP.
3. Configure dependency readiness so database consumers wait for SQL availability. Database readiness must not depend on a domain schema that does not exist yet.
4. Verify EF Core connectivity with a minimal temporary DbContext or connectivity check, without domain tables. Move it into the shared Data library in T02-01. Do not run migrations concurrently from both hosts.
5. Document and test exact startup, shutdown and restart commands, Docker prerequisites, endpoint discovery and volume retention. Complete gate G1 and commit the working stack without rewriting earlier commits.

## Acceptance and checks
- AppHost shows SQL Server, API, MCP and frontend. Health checks, SPA loading and EF connectivity     succeed.
- Restarting does not create duplicate SQL/MCP processes or port conflicts. Configuration does not     depend on a hard-coded random port.
- Backend and frontend builds pass. README matches tested commands and the stage commit hash is     reported.

## Exclusions

Do not launch Copilot analysis at AppHost startup. Domain tables and agent behavior belong to later tasks.
